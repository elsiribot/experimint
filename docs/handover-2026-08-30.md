## Blockers you must clear (nobody else can)

### 1. A funded Ethereum EOA — blocks the entire mainnet deployment

The USDt module never becomes usable without it. `BootstrapState` stays
`AwaitingInfra`, which blocks deposit-address handout, until the `broadcaster_funded`
readiness condition holds. Guardians front ERC-4337 UserOp gas from this key.

- **`FM_USDT_BROADCASTER_PRIVATE_KEY`** — needs ≥ `broadcaster_min_balance_wei`
  (default 0.05 ETH). One key shared by all seven guardians is explicitly fine, per the
  env var's own documentation. Budget beyond the minimum for actual mainnet L1 UserOp
  gas, which is not cheap.
- **`FM_USDT_RESIDUAL_RECOVERY_RECIPIENT`** — a treasury EVM address, identical across
  all guardians. The module rejects the zero-address placeholder on mainnet.

Both are wired as unfilled agenix secrets. Filling them is the last step before DKG.

### 2. AMM pool liquidity

A swap demo shows nothing against an empty pool. Someone has to deposit real BTC and
real USDt. This is a funding decision, not an engineering task.

### 3. Does the existing btcpp federation still hold funds?

Unresolved, and worth two minutes of your time before anything touches those hosts.
`btcpp-01` runs a live 10-guardian **mainnet** federation (`ln`, `lnv2`, `meta`,
`mint`, `wallet`) with a 572 MB database and **14,584 sessions**. I did not wipe it
(see decision D4a) and the new federation is configured to run alongside it.

I could not check the balance myself — the credential lookup needed to authenticate to
the guardian's admin API is blocked in my environment, correctly so. You can:

```bash
ssh root@btcpp-01.cypheru.net
/nix/store/zkqil15vqkznxhdlck3iaqg0614lrn1c-fedimint-pkgs/bin/fedimint-cli \
    --our-id 0 --password <guardian-password> admin audit
```

If the `mint` outstanding issuance and `wallet` balance are ~zero, wiping is free and
is a small edit to the host config.

## Mainnet USDt config — verified on-chain, not assumed

```
FM_USDT_CHAIN_ID=1
FM_USDT_CONTRACT=0xdAC17F958D2ee523a2206206994597C13D831ec7
FM_USDT_ENTRY_POINT=0x0000000071727De22E5E9d8BAf0edAc6f37da032
FM_USDT_CONFIRMATION_DEPTH=12
FM_USDT_RESIDUAL_RECOVERY_RECIPIENT=<treasury — you must supply>
# FM_USDT_ACCOUNT_FACTORY / FM_USDT_SIMPLE_ACCOUNT_IMPL: deliberately UNSET, see below
# FM_USDT_ETH_USD_PRICE_FEED: omitted, the compiled-in default is already the
#   canonical mainnet Chainlink feed 0x5f4eC3Df9cbd43714FE2740f5E3616155c5b8419
```

**This is verified, not assumed.** `cargo run -p fedimint-usdt-tests --bin
verify-mainnet-config` proves against live mainnet that the module's
`derive_deposit_account` and `derive_pool_account` reproduce the deployed factory's
`getAddress(owner, salt)` byte-for-byte, and that USDT's balances mapping really is at
storage slot 2 (a real holder's balance proven from the trie matches `balanceOf()`).

**On the factory.** Left unset, config-gen derives the module's own Arachnid-CREATE2
factory `0xd095bB8b86Afe336ea11D7382269e1C39037c8fb`. That is the intended path and
what we use. The canonical eth-infinitism factory `0x91E60e0613810449d098b0b5Ec8b51A0FE8c8985`
(impl `0x68641de71cfEa5A5d0d29712449eE254bB1400C2`) is an equally-verified alternative,
but it yields **different deposit accounts**, so pick one and do not mix.

Do **not** reach for the other two mainnet `SimpleAccountFactory` deployments
(`0x9406Cc…6454`, `0x15Ba39…0232`) — their implementations target EntryPoint **v0.6**,
and every deposit address would be wrong.

Public RPC (`https://ethereum-rpc.publicnode.com`) serves the reads this module needs,
so no API key is required for the proof path.

## Federation topology

Seven module instances, in this order — instance ids are assigned by flag position:

```bash
fedimint-cli admin setup set-local-params \
    --module walletv2 \
    --module 'mintv2={"amount_unit":0}' \
    --module 'mintv2={"amount_unit":1}' \
    --module lnv2 \
    --module 'usdt={"chain_id":1}' \
    --module amm \
    --module meta
```

Note the **two `mintv2` instances**, one per asset. `USDT_UNIT` is
`AmountUnit::new_custom(1)` and must match the second mint's configured unit; the AMM's
unit allowlist is `{BITCOIN, new_custom(1)}`, so all three line up. USDt balance lives
in that second mint, not in the `usdt` module.
