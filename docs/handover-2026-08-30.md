## Blockers you must clear (nobody else can)

### 1. Four values only you can supply

All are wired as unfilled agenix secrets; filling them is the last step before DKG.

- **`FM_USDT_BROADCASTER_PRIVATE_KEY`** — a funded Ethereum EOA. The hard blocker:
  `BootstrapState` stays `AwaitingInfra`, which blocks deposit-address handout, until
  `broadcaster_funded` holds (≥ 0.05 ETH by default). Guardians front ERC-4337 UserOp
  gas from it. One key shared across all seven is explicitly fine per the env var's own
  docs. Budget well beyond the minimum — this is L1 mainnet gas.
- **`FM_USDT_RESIDUAL_RECOVERY_RECIPIENT`** — a treasury EVM address, byte-identical
  across guardians. The module rejects the zero placeholder on mainnet.
- **A bundler-capable RPC endpoint** (Alchemy / Infura / QuickNode), via
  `services.usdtFederation.evmRpcUrl` + `FM_USDT_EVM_RPC_API_KEY_FILE`.
  **This corrects an earlier claim that the public RPC suffices.** It suffices for
  *deposits* — `eth_getProof` is served by `ethereum-rpc.publicnode.com` and was
  verified working. It does **not** suffice for *withdrawals*.
  `AlloyEvmRpc::get_user_op_receipt` (`modules/usdt/fedimint-usdt-server/src/rpc.rs:1045`)
  calls `eth_getUserOperationReceipt` first and returns `Ok(None)` when it comes back
  empty, so without a bundler-capable endpoint **withdrawals never confirm**. Note the
  module self-bundles — it submits `EntryPoint.handleOps` from the broadcaster EOA, so
  no bundler *service* is needed — but it still uses that method as a hint to locate the
  inclusion block, precisely so the authoritative `eth_getLogs` read can be a cheap
  single-block query within free-tier range limits. The receipt fields themselves are
  always read from the EntryPoint's own `UserOperationEvent`, never trusted from the
  bundler.
- **`FM_PASSWORD_API`** — gates every admin RPC and, unlike the UI password, has no
  disk fallback. The ceremony cannot run without it. Currently commented out in
  `secrets/usdt-config-gen-env.age` so it 401s rather than half-working.

### 1b. Host keys — fixed, but `agenix-rekey` still owes you a step

`btcpp-05` and `btcpp-08` were recipients of nothing, which would have left five of
seven deployable — the threshold with zero margin. Both are now recorded in
`secrets.nix` on `es/usdt-amm-federation`, and all seven guardians are recipients.

Worth knowing why btcpp-08 was previously recorded as uncollectable: its sshd truncates
a keyscan handshake and returns only its RSA key, so `ssh-keyscan -t ed25519` comes back
empty even though the ed25519 key exists. The key was read from the host's own
`/etc/ssh/ssh_host_ed25519_key.pub` instead. btcpp-05's was cross-checked both ways and
agrees.

**Still required:** `just agenix-rekey`. Adding a recipient does nothing until the
`.age` files are re-encrypted. I deliberately did not run it — it re-encrypts every
secret including ones a live guardian depends on, and the USDt secrets are still
placeholders, so it would have to be re-run after you fill them anyway. Agenix
activation fails hard rather than silently, so a premature `just apply` aborts rather
than half-configuring a host.

## The Fedi app port: code complete, blocked on a fedimint re-snapshot

The bridge port is done and compiles — all four API deltas resolved, workspace check,
clippy and fmt clean, UI typecheck and lint clean, AMM swap RPCs and a minimal swap
screen wired. It is on `es/usdt-experimint` in the Fedi repo.

It cannot pass its end-to-end test yet, and the reason is worth understanding because it
was a genuine latent bug in **this** repo, not in the port.

**`fedimint-derive` encodes enum variants by positional index.** Deleting the legacy
observation deposit path removed `UsdtInput::V0`, which renumbered every later variant:
`DepositProofV0` moved from index 2 to index 1. A peer built against the older module
decodes index 1 as `RefundV0`. Both sides still advertised `MODULE_CONSENSUS_VERSION`
`0.12`, so the version handshake accepted the pairing and the mismatch surfaced only as
a deposit submission that hung forever — no error, no rejection, just a wedged deposit
service.

Proved against a baseline: the Fedi base commit passes its USDt e2e in 285 s; the ported
branch fails with `deposit was never proof-credited into USDT e-cash`, and the stall
localises to the first poll that actually submits a proof.

**Fixed here:** `MODULE_CONSENSUS_VERSION` is now `0.13` (commit `a83a3cd`), so a
mismatched pairing fails cleanly at handshake instead of hanging. Adding the fee field to
`DepositProofV0` was a second breaking change under the same version. Both should have
bumped it. When editing a wire enum, append rather than delete or reorder.

**To finish the port**, in order:

1. **Re-snapshot experimint's usdt module into a new `elsiribot/fedimint` tag** based on
   `v0.11.0-fedi9-usdt.1`, and repoint Fedi at it. Nothing else unblocks the e2e, because
   Fedi's test federation runs the usdt *server* vendored in that tag. This is the one
   remaining piece of real work.
2. **Rebase `es/fedi9-compat` onto master** to pick up the `0.13` bump — otherwise that
   branch still ships a module claiming `0.12` with `0.13` wire format, which is the
   exact trap this fixed.
3. Replace the `file://` dependency in Fedi's `Cargo.toml` with a real URL (already
   flagged in-comment there).
4. **Bound the deposit service's submission with a timeout.** A hung submit currently
   wedges every future deposit, defeating the service's never-dies contract. The version
   bump removes this specific cause, but not the class.

The alloy conflict that blocked resolution is **fixed** on `es/fedi9-compat`
(commit `2793f86`). Note the non-obvious part: pinning `alloy-sol-types` alone is not
enough, because `alloy-sol-macro` resolves by ordinary semver and a 1.7.x macro paired
with 1.5.7 types generates calls to ABI methods that do not exist. All five
`alloy-sol-*` crates are locked in step, and the restore command is in that branch's
`Cargo.toml`.

## Operating the guardian-voted fee

Two behaviours you will meet in production that no test failure will warn you about.

**The vote threshold counts configured peers, not online ones.** `consensus_fee_for`
indexes `votes[num_peers.threshold() - 1]`, and `num_peers` comes from `args.num_peers()`
at init. For 7 guardians that index is 5 regardless of how many are reachable. So with
two guardians down, **all five survivors must vote to move the fee** — effective
unanimity among the reachable set. It fails closed to the config fee, which is the right
direction, but it means a fee change is impossible while any guardian is offline in a
tight federation.

This compounds with two other facts in this deployment: hosts have intermittent SSH, and
`btcpp-05`/`-08` currently cannot receive secrets at all. Seed
`default_fee_per_mille` at the value you actually want, and treat voting as an
adjustment mechanism rather than the thing you rely on to set the fee at launch.

**A fee change transiently breaks zero-slippage swaps.** `POOLS_ENDPOINT` and
`QUOTE_ENDPOINT` are read through `request_current_consensus`, which needs threshold-many
byte-identical responses. While a vote propagates, guardians briefly disagree on
`fee_per_mille`, so a client that quotes mid-rollout and submits with
`max_slippage_bps: 0` gets a smaller `dy` than quoted and is rejected. That is correct
fail-closed behaviour, not a bug — but do not schedule a fee change during a demo.

## Federation topology

Seven module instances, in this order — instance ids are assigned by flag position.

**The README's documented invocation does not work, and this is a correctness fix, not
a nit.** `--module 'usdt={"chain_id":1}'` fails DKG with `missing field usdt_contract`:
`set-local-params` passes module params verbatim to `parse_params`, which does a plain
`serde_json::from_value` into `UsdtGenParams` — a struct with **no serde defaults** — so
a partial object is rejected. The `FM_USDT_*` env vars feed `default_config_gen_params`,
which is consulted only on the **setup-UI** path (blank params box → env-derived
defaults) and never on the CLI path. The usdt module therefore needs a *complete* params
file:

```bash
fedimint-cli-experimint admin setup set-local-params \
    --module walletv2 \
    --module 'mintv2={"amount_unit":0}' \
    --module 'mintv2={"amount_unit":1}' \
    --module lnv2 \
    --module 'usdt=@./usdt-params.json' \
    --module amm \
    --module meta
```

The NixOS config renders that file to `/etc/fedimintd-usdt/config-gen-params.json`; the
runbook has a `jq` step substituting the treasury recipient. `mintv2={"amount_unit":N}`
and the paramless modules work exactly as documented.

**Instance ids depend on the path you take.** Via the CLI above they follow flag
position, so `usdt` is instance 4. The in-process test harness instead orders them
kind-alphabetically with extras appended (`amm=0, lnv2=1, meta=2, mintv2(BTC)=3,
usdt=4, walletv2=5, mintv2(USDt)=6`). Any script that hardcodes an id must know which
path produced it.

Readiness is checked with `module_4_usdt_status` over the websocket API. A stock
`fedimint-cli dev api --module 4` cannot do it — the selector resolves against the
client, which has no usdt client module — so the runbook calls the socket directly.

Note the **two `mintv2` instances**, one per asset. `USDT_UNIT` is
`AmountUnit::new_custom(1)` and must match the second mint's configured unit; the AMM's
unit allowlist is `{BITCOIN, new_custom(1)}`, so all three line up. USDt balance lives
in that second mint, not in the `usdt` module.
